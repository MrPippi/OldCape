# OldCape 老披風 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A static, mobile-first gallery of ~30,780 Taiwan Minecraft server player capes, searchable by ID and colour, where each cape downloads as an in-game 64×32 texture.

**Architecture:** A Python pipeline recovers each cape's 22×17 texture region from the 6× previews, de-duplicates, colour-tags, and packs regions into ~500 atlas PNGs plus one `index.json`, committed under `web/public/data/`. A Vite + vanilla TypeScript single page renders capes as integer-scaled CSS sprites from those atlases and builds the 64×32 PNG download in the browser via canvas. GitHub hosts the repo; Cloudflare Pages builds `web/` and deploys `web/dist`.

**Tech Stack:** Python 3.12 + Pillow + fontTools (pytest); Node 20 + Vite 5 + TypeScript 5 (Vitest + jsdom, Playwright); Cloudflare Pages; GitHub Releases.

**Spec:** `docs/superpowers/specs/2026-10-26-oldcape-design.md`

## Global Constraints

- Source assets: `C:\Users\jack3\Downloads\cape\cope` (64 sub-folders). Raw assets are NOT committed; only pipeline output is. *(Plan decision.)*
- Deployed output must stay under **20,000 files** (Cloudflare Pages free plan).
- Capes always render at an **integer scale** with `image-rendering: pixelated`; card aspect ratio fixed 10:16; responsive changes column count, never scale fractionally.
- Scales: wall `<640px` = 4×, `640–1023px` = 5×, `≥1024px` = 6×; hero 14× desktop / 6× mobile; detail 12× desktop / 6× mobile sheet.
- Downloaded file: 64×32 RGBA PNG, 22×17 cape region at (0,0), rest transparent, name `oldcape-{id}.png`.
- Wall sorted by ID ascending; ID search exact match; "今日展出" deterministic per Taipei (UTC+8) date; homepage stats computed from `index.json`, never hard-coded.
- Blank capes (exactly 1 distinct colour in the 22×17 region — Task 4 ruling; ≤2 hid ~1,600 real two-colour designs) hidden from wall, hero and random, but reachable by ID.
- Duplicate content: all IDs kept; lowest ID is canonical; other IDs resolve to the canonical entry.
- 12 colour buckets, bit order fixed: `red, orange, yellow, green, cyan, blue, purple, pink, brown, white, gray, black` (bit 0 … bit 11). Multi-select = AND.
- Fonts: titles Noto Serif TC 900 self-hosted subset, body = device CJK font (Task 10 ruling), accents (logo, `#編號`, stats) Cubic 11 subset; `font-display: swap`.
- UI copy Traditional Chinese only. No accounts, uploads, analytics, 3D preview, image search.
- Performance: mobile Lighthouse performance ≥ 90; LCP < 2.5 s.
- Share URL format: `/?cape={id}`. *(Plan decision.)* "怎麼穿上" and "關於" are sections on the same page (`#how`, `#about`). *(Plan decision.)*
- Coverage ≥ 80% for both `pipeline/` (pytest-cov) and `web/src/data` + `web/src/render` (Vitest).

## Review Focus

1. **Messy ID input** — `#123`, `＃１２３` (full-width), ` 123 `, `abc`: first three find cape 123; `abc` shows "沒有這個編號". → test in Task 5.
2. **Colour filter with zero matches** — show an empty-state message with a 隨機看一件 button, never a silently blank wall. → test in Task 8.
3. **Bad or special share links** — `?cape=abc` ignored (home shown), `?cape={aliasId}` opens the canonical cape, `?cape={blankId}` opens that blank cape. → tests in Tasks 5 and 9.
4. **Atlas not yet loaded / slow network** — cards keep exact final size before images arrive (no layout shift, no misalignment). → test in Task 10.
5. **`index.json` fails to load** — page shows "載入失敗" with a 重試 button instead of an empty page. → test in Task 7.
